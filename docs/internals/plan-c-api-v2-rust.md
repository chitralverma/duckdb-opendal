# Plan: pure-Rust extension on DuckDB's C API v2

Status: **investigation complete, implementation blocked on upstream**. This document records what
was checked, why the move is not possible on DuckDB v2.0.0 as released, what it will take once the
missing API lands, and how to execute it then. It is written to be handed to an agent or
contributor without further context.

Snapshot of the repo this was written against: 0.2.0, DuckDB `v2.0-cyanoptera`, OpenDAL `fce9cde`
(0.59.5). Layout: `src/` C++ shell 2,125 lines, `opendal/` Rust core 4,985 lines, 50 `extern "C"`
entry points, `rust.h` generated by cbindgen, Corrosion-driven CMake, full DuckDB source build on
every CI run.

## 1. What was asked

Could the extension be rebuilt as a pure-Rust extension on the C API v2 (via `duckdb-neo` and
`extension-template-rs`), dropping the C++ shell, the cbindgen/Corrosion plumbing, and the DuckDB
source build, with no functional change, and would DuckDB v2's asynchronous I/O give OpenDAL's
async core a more natural fit?

## 2. Findings

### 2.1 Async I/O does not touch the file-system interface

DuckDB v2's asynchronous I/O (blog post 2026-07-31) is implemented *above* `FileSystem`. The
Parquet and CSV readers build read-ahead queues of fetch tasks and run them on a separate ASYNC
thread pool (`async_threads`, default `4 * threads`, capped at 256). Each fetch task still calls the
ordinary, synchronous `FileHandle::Read(buffer, nr_bytes, location)` on that pool thread
(`extension/parquet/parquet_reader.cpp::CollectIOTasks` wraps `read_head->Fetch(*file_handle)` in a
`CallbackAsyncTask`; the fetch bottoms out in `CachingFileHandle::Read`, which calls
`file_handle->Read(...)`). There is no async virtual on `FileSystem` in v2.0.0, in C++ or in the C
API.

Consequence: our `block_on` per positioned read is already the right shape. DuckDB parallelises
*across* reads by issuing many at once from the ASYNC pool; each one is a blocking call into us.
What we gained from v2 is that those calls now arrive concurrently on one handle, which PR #35 made
explicit (`od_reader_read` takes `&self`). A pure-Rust port would not change the I/O model, only the
packaging. The "OpenDAL is async anyway" intuition is correct but the dividend is already collected.

### 2.2 The C API v2 in v2.0.0 lets extensions *use* a file system, not *provide* one

Checked in the pinned `duckdb/src/include/duckdb_v2.h` and the published reference
(`docs/2.0/clients/c/v2/api`). The `File System` module exposes:

- `duckdb_v2_{instance,connection,context}_get_file_system`
- `duckdb_v2_file_system_open / path_exists / path_is_remote / path_expand / path_glob /
  path_move / path_remove`
- `duckdb_v2_file_{read,write,read_at,write_at,tell,size,seek,sync,close,destroy}`

All of these take a borrowed `duckdb_v2_file_system_handle` obtained *from DuckDB*. There is no
`register` for file systems. The complete list of `duckdb_v2_*_register_*` symbols in the header is:
aggregate, cast, copy, custom_option, custom_type, log_sink, macro, multi_file_function, pragma,
replacement_scan, scalar, table. `duckdb-neo`'s `file.rs` mirrors this exactly (consumer only), and
`extension-template-rs` demonstrates none of it because there is nothing to demonstrate.

The same is true of the stable v1 C API (`duckdb.h`, `MODULE: file_system`): consumer functions
only.

So on DuckDB 2.0.0 a pure-Rust extension cannot serve `s3://`, `fs://` or any scheme through
DuckDB's VFS. The core of this extension, `OpenDalFileSystem : public FileSystem`, has no C-API
equivalent yet.

### 2.3 The provider API exists upstream as an open PR

The maintainers' answer to "filesystem registration" in the C API v2 feedback thread
(duckdb/duckdb discussion 27525) is https://github.com/duckdb/duckdb/pull/25916, "C-API-V2: Add
custom file system support" (opened 2026-09-18, last pushed 2026-10-18, open, no reviews yet, CI
mostly green, no milestone). Its spec (`api_spec/v2/filesystem/virtual_file_system.yaml` at head
`8977341`) defines a `duckdb_v2_vfs` builder with:

- registration: `vfs_create_with_extension`, `vfs_set_name`, `vfs_add_prefix`,
  `vfs_set_claim_callback`, `vfs_set_user_data`, `vfs_register`, `vfs_destroy`
- path callbacks: `claim`, `stat`, `list`, `glob`, `remove_file`, `create_directory`,
  `remove_directory`, `move`
- file callbacks: `open`, `close`, `abort`, `read_at`, `write_at`, `stat`, `sync`, `truncate`
- `vfs_file_open_set_property(IS_SEEKABLE | IS_ON_DISK)`, `vfs_file_open_set_data` (per-file
  state with destructor), `vfs_info_try_get_context`, `vfs_info_get_file_system` (delegation)
- file metadata is a first-class handle (`file_metadata_set_{type,size,last_modified,version_tag,
  value}`) and listings carry metadata per entry (`file_listing_add_entry`), so the glob/list ->
  open metadata handoff we built in PR #35 maps 1:1 (`open` receives "whatever the glob callback
  filled in about the entry").

Design notes from the spec that matter for us: all I/O is positional and the engine keeps the
cursor; `FILE_FLAG_PARALLEL_ACCESS` means callbacks may run from several threads on one file;
`IS_SEEKABLE=false` yields exactly our append-only writer contract (every `write_at` lands where
the previous one ended); missing-path semantics per callback are spelled out; a VFS registration
lasts for the instance lifetime.

This covers every `FileSystem` virtual we override today, including the v2 additions
(`AbortFileWrite` -> `abort`, `GetVersionTag`/`Stats` -> `file_stat` + metadata version tag,
`GetStatsIfExists` -> `stat`, `ListFilesExtended`/glob metadata -> listing entries with metadata).

### 2.4 What else the extension needs from the host, and v2 coverage today

| Capability we use | C++ API today | C API v2 (2.0.0) | Notes |
| --- | --- | --- | --- |
| Register a VFS for `fs://`, `s3://`, ... | `RegisterSubSystem` | **missing** (PR 25916) | blocker |
| Scheme override vs httpfs (`IsManuallySet`) | yes | PR 25916: last-registered-wins + `claim` callback | semantics differ; see 4.3 |
| `CREATE SECRET (TYPE s3, config MAP{...})`, SCOPE lookup | `SecretManager` | **missing** | maintainers: "planned, waiting on internal changes" |
| `SET opendal_*_config` globals | `AddExtensionOption` | `custom_option` | covered |
| Table functions `opendal_ls/stat/du/copy/info/schemes` | `TableFunction` | `table_function` (95 symbols) | covered |
| Scalar `opendal_version`, `opendal_is_manually_set` | `ScalarFunction` | `scalar_function` | covered |
| Logging (`DUCKDB_LOG_FILE_SYSTEM_*`, warnings) | logger | `context_log(type string)` | covered, less structured |
| `async_threads` for runtime sizing | `DBConfig` | `config_get_option_value` | covered |
| External file cache etag validation | `GetVersionTag` | `file_metadata_set_version_tag` (PR) | covered once PR lands |
| Exclusive create -> `if_not_exists` | `FileOpenFlags` | `FILE_FLAG_EXCLUSIVE_CREATE` in open flags list | covered |

Two blockers, one hard and one soft:

1. **VFS provider API**: hard blocker. Nothing to build on until PR 25916 (or a successor) merges
   and ships in a release.
2. **Secrets API**: soft blocker. Without it the only options are (a) `custom_option` settings
   per service, which loses SCOPE matching and the `CREATE SECRET` UX users already have, or (b)
   `vfs_info_try_get_context` + running SQL to query `duckdb_secrets()`, which the maintainers
   explicitly ruled out ("Running SQL from inside a callback doesn't make sense"). Either is a
   functional regression, so the move should wait for secrets as well, or ship with a documented
   configuration change.

### 2.5 Build and maintenance gains, quantified

Confirmed against `extension-template-rs` (`a679601`, 2026-11-13) and
`extension-ci-tools/makefiles/c_api_extensions/`:

- **No DuckDB source build.** `libduckdb-sys` with `loadable-extension-v2` generates bindings from
  the bundled `duckdb_v2.h`; the extension is a `cdylib` built by cargo, then a script appends the
  DuckDB metadata footer. Tests run against a pip-installed `duckdb==<TARGET_DUCKDB_VERSION>` via
  `duckdb_sqllogictest`. Our current CI builds the full DuckDB tree (the `SQL tests` job took 19m51s
  on the last PR, mostly that build); the template's equivalent is a cargo build plus a pip
  install.
- **No CMake, Corrosion, cbindgen, or `rust.h`.** `CMakeLists.txt` (170 lines), `build.rs`, the
  generated header, and the 50-function `extern "C"` surface with its `ffi_guard!`/`OdError`
  discipline all go away. The Rust core keeps `operator.rs`, `config/*`, `uri.rs`, `capability.rs`,
  and most of `table.rs`; `reader.rs`/`writer.rs`/`stat.rs`/`lister.rs`/`mutate.rs` become
  callback bodies rather than FFI exports.
- **Estimated size**: the ~2,125 lines of C++ disappear; the Rust core shrinks because every
  `*mut T` handle, out-param error, and `cstr()` decode is replaced by `duckdb-neo` types. Rough
  target: 3,000 to 3,500 lines of Rust total, one crate, versus 7,100 lines across two languages.
- **ABI stability**: once the symbols we use are marked stable, binaries stop needing a rebuild per
  DuckDB patch release. Today every v2.0.x patch rebuilds everything. This does not apply until the
  VFS and secrets modules are stabilised, which will lag their first appearance.
- **WASM**: the template builds `wasm_eh` out of the box; our CMake path has a `WASM_BUILD` branch
  that has never been exercised in CI.

### 2.6 Performance: no change expected in the hot path

Reads: C++ `Read` -> `od_reader_read` -> `block_on(read_into)` becomes
`read_at` callback -> `block_on(read_into)`. Same one copy into the engine-owned buffer (the
`vfs_file_read_at_callback` buffer is "engine-owned"), same runtime hop. Writes: same append-only
writer with `IS_SEEKABLE=false`. The per-open and per-glob savings from PR #35 carry over because
the spec threads listing metadata into `open`.

Where it could be *slower*: callbacks cross C ABI with `duckdb_v2_str` views and error-info
handles per call, which is comparable to today's FFI, not cheaper. Where it could be *faster*: none
identified. The gain is maintenance and build time, not throughput. The IMPROVEMENTS backlog (P9
benchmark harness, issue #34) should land first so the port can be measured for regressions.

## 3. Decision

Do not start the port on DuckDB 2.0.0. Track PR 25916 and the secrets API. Re-evaluate when
**both** are in a tagged DuckDB release and `duckdb-neo` exposes them (today `duckdb-neo` has no
VFS wrapper at all; a `vfs.rs` would have to be contributed or written locally against
`libduckdb-sys` raw bindings).

Trigger to revisit this plan: a DuckDB release whose `duckdb_v2.h` contains
`duckdb_v2_vfs_register`. Check with
`curl -sL https://raw.githubusercontent.com/duckdb/duckdb/<tag>/src/include/duckdb_v2.h | grep -c vfs_register`.

## 4. Execution plan (for when the trigger fires)

### 4.1 Prerequisites

- DuckDB tag `T` with `duckdb_v2_vfs_*` and a secrets module in `duckdb_v2.h`.
- `duckdb-neo` version matching `T` (`=1.<T>.x` versioning), or a local `vfs.rs` over
  `libduckdb-sys` if upstream has not wrapped it.
- `extension-ci-tools` at the branch for `T`; the Rust `c_api_extensions` makefiles.
- Benchmark baseline from #34 on the current C++ build, same machine, so the port has numbers to
  match.

### 4.2 Repository shape after the port

```
Cargo.toml                       workspace: core, native, wasm (template layout)
crates/core/src/
  lib.rs                         extension entry: register VFS, options, table/scalar functions
  vfs.rs                         duckdb_v2_vfs builder + the 16 callbacks
  operator.rs, config/, uri.rs, capability.rs   unchanged in spirit
  reader.rs, writer.rs           bodies of read_at / write_at / close / abort / sync
  stat.rs, lister.rs, mutate.rs  bodies of stat / list / glob / remove / mkdir / move
  table.rs                       opendal_ls / stat / du / copy / info / schemes via table_function
  secrets.rs                     secret type registration + scope lookup (new API)
  options.rs                     opendal_*_config, opendal_override_native_filesystems
Makefile                         includes c_api_extensions/{base,rust}.Makefile
test/sql/**                      unchanged; runner becomes duckdb_sqllogictest
test/services/**                 unchanged
```

Deleted: `src/`, `CMakeLists.txt`, `extension_config.cmake`, `opendal/build.rs`, `cbindgen.toml`,
`vcpkg.json`, the `duckdb` and C++ `extension-ci-tools` submodules.

### 4.3 Semantics to re-decide

- **Scheme ownership.** Today `IsManuallySet()` returns true only for schemes in
  `opendal_override_native_filesystems`. In the VFS spec, the *last registered* VFS whose prefix or
  `claim` callback matches wins. Load order between `opendal` and `httpfs` therefore decides
  `s3://`. Implement `claim` to return true only for (a) schemes httpfs does not own, or (b) schemes
  listed in the override setting, and document that the setting must be set before the first
  access. `opendal_is_manually_set()` keeps working.
- **Secrets.** Port `TYPE <scheme>` + `config/io_config/retry_config/timeout_config/cache_config`
  MAPs onto whatever the secrets API offers. If it lacks per-type named parameters, fall back to a
  single `TYPE opendal` with a `scheme` field and document the migration. SCOPE matching must stay.
- **Logging.** `context_log` with a type string replaces `DUCKDB_LOG_FILE_SYSTEM_*`; the
  `logging.test` assertions will need their expected log type names adjusted.
- **Operator cache lifetime.** Today it lives on the `OpenDalFileSystem` instance (one per
  database). With `vfs_set_user_data` the cache lives on the VFS user data, same lifetime. Keep the
  `scheme://authority#digest` key from PR #35.
- **Runtime.** `vfs_info_try_get_context` is available in callbacks; read `async_threads` from the
  instance config at registration instead of at load.

### 4.4 Steps

1. Branch `feat/capi-v2`. Copy `extension-template-rs` scaffolding (workspace, `Makefile`,
   `.github/workflows/MainDistributionPipeline.yml`, `extension-ci-tools` submodule).
2. Add `duckdb-neo` with `build-extension`; if it lacks VFS, add `crates/core/src/vfs_sys.rs`
   binding the `duckdb_v2_vfs_*` symbols from `libduckdb-sys` raw bindings behind a thin safe
   wrapper. Upstream it to `duckdb-rs` in parallel.
3. Move `opendal/src/{operator,config,uri,capability}.rs` into `crates/core/src/` unchanged. Delete
   `ffi.rs`, `error.rs`'s out-param machinery, and every `#[no_mangle]`.
4. Implement callbacks in this order, running `make test` against `fs.json` after each group:
   `claim` + `open` + `read_at` + `close` + `file_stat` (reads work) -> `stat` + `glob` + `list`
   (globbing works) -> `write_at` + `sync` + `abort` with `IS_SEEKABLE=false` and
   `FILE_FLAG_EXCLUSIVE_CREATE` -> `if_not_exists` (writes work) -> `remove_file`,
   `remove_directory`, `create_directory`, `move` (mutations work).
5. Register `opendal_*_config` and `opendal_override_native_filesystems` as custom options;
   re-implement the option-change callbacks.
6. Port table functions from `table.rs` + `opendal_table_functions.cpp` onto `duckdb-neo`'s
   `table_function` API; `opendal_version` / `opendal_is_manually_set` / `opendal_schemes` as
   scalar/table functions.
7. Secrets per 4.3.
8. Run the full tier ladder (`fs`, `memory`, `s3`, `azblob`, `gcs`, `http`) and the request-count
   assertions in `s3.test`; numbers must match the C++ build exactly.
9. Run the #34 benchmark; any regression over 5% on `fs://` or MinIO blocks the merge.
10. Update `README`, `CONTRIBUTING` (build is now `make` -> cargo; no DuckDB checkout),
    `MAINTAINING` (axis A becomes "bump `TARGET_DUCKDB_VERSION` + `duckdb-neo`"; axis B unchanged),
    the two skills, and the compatibility matrix. Release as a minor bump; the loadable is a
    different artifact kind and the community registry entry changes build type.

### 4.5 Acceptance

- `make test` green on all six tiers with the sqllogic files unchanged except documented log-type
  names.
- `s3.test` request-count assertions unchanged (0 HEAD per globbed read, 0 per-file DELETE on
  OVERWRITE).
- `SELECT opendal_version()` reports the same OpenDAL rev.
- No `duckdb/` source checkout anywhere in the build; CI `SQL tests` wall time under 5 minutes.
- Benchmark within 5% of the C++ build on `fs://` and MinIO.

## 5. What to do in the meantime

Keep the C++ shell thin and the Rust core self-contained so the port is a re-skin, not a rewrite:

- New behaviour goes in `opendal/src/*` behind a narrow `extern "C"` entry; the C++ side stays
  glue. (PR #35 followed this: all logic for extended metadata, batch delete, io defaults is Rust.)
- Avoid new DuckDB C++ types in the Rust-facing structs (`OdMetadata`, `OdEntry`, `OdCopyOptions`
  already mirror what the VFS spec's `file_metadata` carries).
- Land #34 so the port has a baseline.
- Subscribe to PR 25916 and discussion 27525; when the VFS spec lands, open a `duckdb-rs` issue
  (or PR) for a `vfs` module in `duckdb-neo` so the Rust side is ready when the C side ships.
